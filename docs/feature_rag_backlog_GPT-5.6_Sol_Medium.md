# RAG Feature Review Backlog — GPT-5.6 Sol Medium

Review scope: the implemented RAG follow-up feature against the 14-point plan and `docs/PROJECT_GUIDE.md`.

This backlog intentionally includes only High- and Medium-priority findings. Items are ordered by implementation priority.

## P1 — High: Do not report successful resolution when the database update fails

**Status:** TODO

**Locations:**
- `app/agent/nodes/dialog_end.py:35-59,85-98`
- `app/api/routes/tickets.py:219-228`

**Problem:** `dialog_end` returns a `resolve_failed` error when the ticket cannot be updated, but the chat endpoint ignores that error. The client can receive HTTP 200, `done=true`, and a success message while the ticket remains unresolved. Since `dialog_closed` is already checkpointed, the user cannot retry through chat.

**Relevant requirements:** Plan Step 8; PROJECT_GUIDE success-close contract.

**Acceptance criteria:**
- A failed `resolved` status update is visible to the API caller and is not presented as a successful resolution.
- The checkpoint and ticket status cannot end in a contradictory, unrecoverable state.
- The healthy success-close path still returns `done=true` and persists `status=resolved`.
- Automated tests cover missing session, missing ticket, and CRUD exception paths through the graph/API boundary.

## P2 — Medium: Match goodbye phrases as words, not arbitrary substrings

**Status:** TODO

**Location:** `app/agent/nodes/chat_handler.py:207-209`

**Problem:** The current substring check treats ordinary words containing `пока` as goodbye. For example, `Покажите настройки` can close the dialog. On ticket creation this can stop classification and persistence; on follow-up it can close an active support conversation.

**Relevant requirement:** Plan Step 3 close detection.

**Acceptance criteria:**
- Explicit farewell phrases such as `пока` and `до свидания` still close the dialog.
- Words such as `покажите` do not trigger goodbye.
- Existing precedence remains: escalate → success → goodbye → turn cap.
- Unit tests cover explicit farewells, punctuation/case variants, and substring false positives.

## P3 — Medium: Prevent stale RAG citations on non-RAG responses

**Status:** TODO

**Locations:**
- `app/agent/nodes/chat_handler.py:105-119,172-174`
- `app/api/routes/tickets.py:204-227,248-257`

**Problem:** Close, validation, and injection paths do not update `rag_used` or `rag_source_paths`. LangGraph therefore preserves values from the previous grounded turn, and the API can return old source paths as if they support the current fixed or fallback response.

**Relevant requirements:** Plan Steps 10 and 11; `ChatResponse.source_paths` citation contract.

**Acceptance criteria:**
- `source_paths` describes only the response produced by the current turn.
- Non-RAG responses clear or otherwise omit stale RAG metadata.
- A grounded response still returns deduplicated source paths.
- A checkpointed multi-turn test covers RAG hit → success/goodbye/turn-cap and verifies that old citations are not returned for the closing response.

## P4 — Medium: Evaluate an actual generated grounded answer

**Status:** TODO

**Location:** `scripts/eval_rag.py:137-145`

**Problem:** The Ragas dataset currently assigns the hand-written `reference` to `response`. Context precision and context recall still provide useful retrieval evaluation, and faithfulness measures whether the canonical answer is supportable by retrieved context. However, faithfulness and answer relevancy do not assess an answer generated by SupportAI, so grounded-prompt or generation regressions can pass unnoticed.

The current answer-relevancy result is also poorly calibrated for Russian because it combines an Ollama reverse-question judge with the primarily English `all-MiniLM-L6-v2` embedding model. Low scores should not automatically be interpreted as poor application answers.

**Relevant requirement:** Plan Step 13 optional RAG quality evaluation.

**Acceptance criteria:**
- Evaluation obtains `response` from the same grounded prompt/LLM path used by the feature, or from an explicitly equivalent evaluation adapter.
- `reference` remains independent ground truth.
- Retrieval-only mode remains available and does not require Ollama.
- Results clearly separate retrieval metrics from generation metrics.
- The embedding model used for answer relevancy is suitable for Russian, or the limitation is explicitly documented and the metric is excluded from release decisions.
- At least one controlled bad generated answer produces a materially worse faithfulness/relevancy result than a correct grounded answer.

## Uncertainties and follow-up verification

- Live Qdrant ingestion, model download, and the full Ragas/Ollama evaluation were not rerun during the code review. Re-run them after changing the evaluation pipeline.
- The three documented Postgres/Qdrant E2E scenarios were reported as manually successful but are not covered by an automated integration suite.
- Docker networking is not fully demonstrated: `QDRANT_URL=http://localhost:6333` works for local uvicorn, but a containerized app requires a reachable host or service hostname.
- Concurrent requests for the same `thread_id` were not tested. Verify whether checkpoint updates serialize correctly or can lose message/count updates.
